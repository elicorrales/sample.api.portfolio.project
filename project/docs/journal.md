# Project Journal

How this project came together, step by step. Each step links to the detailed record.

Written in my voice: **I** means me, the project author, and **the AI** means Claude in Claude Code. See the [decision log key](decisions/README.md#whos-who).

## 2026-09-12 — From idea to spec

| # | Step | What happened | Record |
|---|---|---|---|
| 1 | Initial plan | Sketched the project with a different AI assistant: a Node/Express/PostgreSQL users API, built test-first. | [01](decisions/01-ai-cross-check.md) |
| 2 | Second opinion | Gave that whole chat to Claude to confirm or dispute. It caught an outdated claim about Node's test tooling, and several items the plan put off too long (validation, auth). | [01](decisions/01-ai-cross-check.md) |
| 3 | Stack and tests | Learned what each tool does. Defined my own test categories: happy path, bad calls, integrity, security, performance, rate limiting. | [02](decisions/02-stack.md), [03](decisions/03-test-strategy.md) |
| 4 | Scope | Chose an admin-only API first; self-service logins later. | [04](decisions/04-admin-vs-self-service.md) |
| 5 | Hosting | Planned local first, then Render (API + Swagger UI) and Netlify (pages), the services I already use. Identified the problem of letting demo visitors use an admin API. | [05](decisions/05-hosting.md) |
| 6 | Code layout | Had the AI compare the folder structure of my three earlier projects before proposing one for this API. | [06](decisions/06-layering.md) |
| 7 | User rules | Worked through fields, views, search, delete/restore, and locking in short question-and-answer rounds. **Key moment:** choosing optimistic locking removed PATCH's main advantage, so I chose PUT. | [07](decisions/07-users.md) |
| 8 | Phones and addresses | Set ownership, delete, and validation rules. Tightened several suggestions: one phone per type, 3 addresses max, 5-digit ZIP only. | [08](decisions/08-phones-addresses.md) |
| 9 | Record keeping | Decided repo docs are the record and AI memory holds only pointers. Backfilled this decision log from the conversation. | [09](decisions/09-docs-and-process.md) |
| 10 | Credit audit | Reviewed who each decision came from. The AI had credited me for several choices I had actually picked from its options, so I added a **picked** tag and retagged those decisions. | [Decision log key](decisions/README.md#whos-who) |
| 11 | Tooling fix | The Claude Code diff panel couldn't read git. Cause: the repo sits in a VirtualBox shared folder, where files appear owned by `root` and marked executable. Fixed with git's `safe.directory` and `core.fileMode false`. | — |
| 12 | Operations list | Turned the decisions into a plain-language list of all 16 operations, the step before the formal OpenAPI file. Filling in details surfaced five new questions; I accepted all five proposals. | [Operations](spec/operations.md) |
| 13 | HTTP conventions | The AI mapped the operations to paths, methods, and status codes, with 8 convention choices. Before accepting, I checked each choice from two angles: security and the future web client. That surfaced five extra rules (page size cap, sort allowlist, auth before existence, no leaked internals, CORS headers). **Pushback:** I challenged the AI's claim that the standard error format wasn't JSON. It is; the AI corrected its framing. | [10](decisions/10-api-conventions.md) |
| 14 | Docs page first | Before writing any endpoints, set up a Swagger UI page on the portfolio site that renders the spec, so the contract is visible (and hostable) from the first line. **Pushback:** the first version required copying the spec by hand before every local view. I rejected that, and the page now loads the spec from one path that works both locally and on Netlify. | [05](decisions/05-hosting.md#viewing-the-spec-before-the-api-exists) |
| 15 | Spec piece 1: shared parts | Wrote the reusable parts every endpoint will reference: admin token, error format, paging, IDs, version header, standard error responses. Ran a spec linter (Redocly) to check the file against OpenAPI rules; it flagged a missing server list and license, which led to adding `localhost:3000`, choosing MIT, and making linting a standing step. | [10](decisions/10-api-conventions.md#shared-components-spec-piece-1) |
| 16 | Spec piece 2: user endpoints | Wrote the 6 user operations into the spec. I questioned the proposed 100-character name limit ("what's realistic?"), which led to 50 per field, plus character rules that don't block real names like José, O'Brien, or García-Fernández de la Torre. The name pattern was tested against sample names before acceptance. | [07](decisions/07-users.md#field-details-spec-piece-2) |
| 17 | Spec piece 3: phones and addresses | Wrote the remaining 10 operations; the spec now has all 16 and passes the linter. Writing exact validation exposed a conflict between two earlier rules: "no duplicates" plus "one per type" would have blocked the common case of home address = mailing address. The duplicate rule was dropped. | [08](decisions/08-phones-addresses.md#details-and-a-reversal-spec-piece-3) |
| 18 | No formal spec review | I pushed back on a full spec review: it's greenfield, writing tests is itself a review, and the admin web client will prove the spec in real use. The spec stays at 0.x until then, and becomes 1.0.0 once verified end to end. | [03](decisions/03-test-strategy.md#formal-spec-review-skipped) |
| 19 | Database without Docker | No Docker and little disk space. Briefly considered MariaDB, but kept PostgreSQL (hosting support, earlier decisions). Chose a staged path: in-memory fakes, then PGlite (PostgreSQL inside Node), then a native PostgreSQL install. | [03](decisions/03-test-strategy.md#database-path-for-tests) |
| 20 | Test setup and first red test | Set up Vitest, Supertest, and TypeScript, plus an app skeleton that answers `501` to everything, and wrote the first happy-path test (create a user). `npm install` failed in the VM because the VirtualBox shared folder blocked symbolic links; fixed by enabling symlinks for that share on the host. I ran the test myself: it failed with `expected 501 to be 201`, which is the intended red: the test runs and fails for the right reason. | [02](decisions/02-stack.md#confirmed-at-test-setup) |
| 21 | One user form, one save | While planning the happy-path tests, I pictured how the admin page will actually be used: one form for create and edit, with all the user's info, and one Save. The spec didn't match: phones and addresses had their own endpoints, so a user could exist with none, or lose their primary. **Key moment:** thinking about real use, not just tests, reversed several earlier rules before any code was written. Phones and addresses are now saved as part of the user (at least one of each, exactly one primary, automatic when there's only one), with no ids of their own. **16 operations became 6.** Updated the decisions, operations list, spec (lint passes), and the first test, which I re-ran: still red for the right reason. | [08](decisions/08-phones-addresses.md#revision-one-user-form-one-save) |
| 22 | First vertical slice | After two red tests for create user, I noticed we had been going layer by layer (spec, then tests) and asked to go the other way: enough real code for one operation to work end to end, on a real server, called from the Swagger page. That's a **vertical slice** (also called a walking skeleton). Added a second test (3 phones and 3 addresses, sent out of order), which exposed a spec gap: "sorted by type" never said in which order (chose the listed order). Built create user through every layer: Zod validation, business rules, an in-memory repository, JWT auth, hand-written CORS, and Problem Details errors. The other 5 operations still answer `501`. Both tests went green on my run. Then I started the API, served the docs page, pasted a dev token (`npm run token`) into Swagger's Authorize, and created a user: `201`, then `409` on the same email. Restarting the API clears the data, as expected with in-memory storage. | [06](decisions/06-layering.md#as-built-first-vertical-slice-create-user) |
| 23 | Plain English characters | Planning the List tests raised questions about accents (does `garcia` find `García`? where does `Élise` sort?). I stepped back and decided that supporting every language was more than a sample project needs: names now allow only A–Z, spaces, hyphens, periods, and the straight apostrophe; street and city allow letters, digits, spaces, and `- , . #`. This reverses the "letters in any language" rule. While at it, settled two List questions: sorting ignores case, and a page past the end returns an empty page instead of an error. I asked how the web client would know when to show a page-nav (`<< < 1 2 3 > >>`); the existing response (`page`, `totalPages`, `totalItems`) already covers it, so the spec's list shape didn't change. | [07](decisions/07-users.md#revision-plain-english-letters-only), [10](decisions/10-api-conventions.md) |
| 24 | List users | Added a `createUser` test helper so each test sets up only the users it needs. Wrote 5 List tests (default order, search, sort by email descending, paging, page past the end); ran them red (`501`), then the code was built and all 7 tests went green. One small question came up: with `order=desc`, do tie-breakers reverse too? Kept them ascending (Smith Bob before Smith Zoe). Tried it several times from Swagger UI. | [07](decisions/07-users.md#listing) |
